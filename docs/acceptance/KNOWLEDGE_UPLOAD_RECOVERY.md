# 招聘资料库上传中断修复（2026-11-16）

## 现象和证据

用户上传第4份学习素材时报错。11月10日15:00:25的Java日志为`ResourceAccessException / Unexpected end of file from server`，调用栈位于`QdrantVectorStore.ensureCollection`。相邻Qdrant日志显示，旧实现每段写入前都会PUT创建已存在的knowledge集合并收到409，正常写入随后返回200；报错那次没有对应成功写入记录。

已确认异常属于向量库HTTP传输阶段，不能据此归因于第4份文件内容。历史TCP连接为何断开无法从现有日志单独定论，不将“偶发连接中断”声称为已彻底消除。

## 修复

- 改用JDK HTTP客户端，保持3秒连接/15秒读取超时，替代原HttpURLConnection路径。
- 首次GET检查集合，存在则复用；仅404时创建，409兼容并发创建；后续缓存检查结果，不再逐段反复创建。缓存后集合被移除时只重新检查/恢复一次。
- 对Qdrant传输异常最多重试一次，只重试同一幂等HTTP请求。upsert复用原pointId与请求体，查询为只读、删除使用相同过滤器。不会重新请求Embedding或重复整次资料上传；400等请求错误不盲目重试。
- 持续不可用返回503、`VECTOR_STORE_UNAVAILABLE`及`Retry-After`，前端显示可理解提示。已有上传租约和清理机制继续负责失败数据隔离与补偿。
- 资料上传超时由普通接口30秒改为专用300秒；客户端断线时提示先刷新列表核对，不自动重传，不把未知结果当作确定未完成。
- 生产配置显式覆盖MyBatis SQL日志，避免日志被资料正文和大段向量淹没。模型密钥、代理、数据库结构均未更改。

## 回归与范围

新增10项确定性HTTP故障回归：集合复用/缺失创建、响应丢失后相同pointId重试、持续失败次数与503、400不重试、集合检查失败、创建响应丢失后的409、缓存集合失效、已不存在集合的删除和只读查询恢复。

`scripts/verify-knowledge-upload-ui.py`使用模拟API验证503提示、断线提示、300秒预算、刷新不自动重传及手动恢复成功。Python跨服务测试显式隔离继承代理，保证本地模拟服务不受宿主机代理配置影响，不修改运行环境的真实代理。

真实复测入口为`python scripts/verify-live-knowledge.py`，会创建独立虚构测试账号并逐份上传7份学习资料，实际调用向量化与一次带来源问答；状态保存于被忽略的`outputs/acceptance/knowledge-时间戳/`。可用`--resume 路径/state.json`恢复，先核对已有文档，避免重复上传。用户原有资料不覆盖、不重复导入。

自动重试只提高有限瞬断下的恢复能力，不保证长时间断网时仍上传成功。持续断网应明确失败并由用户刷新核对，不能无限重试或伪造成功；本次未修改外部网络基础设施。
