# 文档一致性与岗位并发修复（2026-11-09）

## 变更行为

上传不再吞掉数据库异常。向量调用前创建UPLOADING租约；完成向量写入后，在独立数据库事务中保存全部切片、元数据与简历发布回调，提交完成才返回。任何持久化失败回滚SQL并登记PENDING清理，不把部分写入当作成功。简历解析、Embedding及向量调用在事务外，发布前重新锁定岗位，岗位已被删除时不写孤立简历。

删除文档/简历时，元数据隐藏、切片删除、向量清理任务与调用者SQL事务一起提交；数据库失败则整体回滚，不再继续删除简历。删除提交后RAG依据数据库有效文档、owner及清理状态过滤候选，在精排和返回正文之前排除已删除、未发布及孤立向量。数据库不可用时拒绝返回检索结果。

向量物理删除异步执行，默认每5秒扫描最多20项；失败记录attempts并60秒后重试，未完成任务会保留。上传每段写入后续租15分钟；进程中断的过期上传、执行中失联5分钟的清理任务可再次领取。领取使用独立token，旧执行者不能删掉新任务；外部删除幂等。旧数据中没有元数据的向量会被过滤，本次不批量删除未登记的历史点。

这是一种“数据库控制可见性、向量物理删除最终完成”的实现，不是跨MySQL/Qdrant分布式事务。查询过滤可能在清理积压时减少召回数量，后台清理成功后恢复。现有聊天历史或已经返回客户端的内容不被追溯撤回；重试不等同于备份或合规审计保留。

岗位编辑在锁内保留最新OPEN/CLOSED状态；关闭操作同样锁定岗位，仅更新状态与时间。两者交错时保留新标题且岗位最终关闭，不引入自动重新开启。

生产Compose新库改挂载`deploy/local/01-schema.sql`，避免将H2兼容的`CREATE INDEX IF NOT EXISTS`交给MySQL8。测试校验该脚本与应用表结构一致，并执行完整兼容结构初始化；不把H2验证称为真实MySQL启动验证。

## 部署与运维

清理使用专用单工作线程与防重入标记，不占用招聘任务的共享调度线程，也不积压无界任务。Qdrant请求设置3秒连接、15秒读取超时，服务停机时停止清理线程；持久记录仍保留供下次恢复。

已有库备份后执行`deploy/migrations/20261109_document_lifecycle.sql`，然后更新后端。新库初始化已包含该表。无需新外部服务或密钥，清理任务沿用应用调度器；test profile关闭自动调度，通过测试显式驱动。

配置：`knowledge.cleanup.enabled`默认true，`knowledge.cleanup.poll-ms`默认5000。后台清理不依赖请求用户SecurityContext，只按已授权登记的documentId执行。不要在生产关闭清理后将“逻辑删除成功”误认为物理清理完成。

只读检查：`SELECT state, COUNT(*) FROM document_vector_cleanup GROUP BY state;`；重试统计见attempts、next_attempt。数据库和向量服务恢复后自动重试。本轮未修改既有数据，也未自动回填或清理历史记录。
