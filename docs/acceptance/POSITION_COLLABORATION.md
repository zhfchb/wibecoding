# 岗位只读协作验收（2026-11-08，第四阶段A）

## 交付范围

招聘资料默认创建人可见。创建人在岗位详情“协作授权”中选择本公司其他成员，授予或撤销该岗位只读权限；HR也可以为自己创建的岗位授权。公司管理员、系统ADMIN不因此自动获得同事资料。

获授权成员的工作台列表包含该岗位，标记“只读协作”，可查看岗位、候选人结构化资料、匹配结果和已有面试题/报告。不能上传/删除简历、修改/关闭/删除岗位、更换部门、筛选决策、生成资料、提交/查看/取消创建人的后台任务或转授权。页面隐藏这些入口，后端各写接口仍校验创建人。

本阶段没有写协作、负责人转移、面试官角色、全公司人才池或共享知识库。私人知识库、聊天、向量ownerId和Python带服务令牌的检索回调保持原隔离边界；用户JWT不能代替内部服务令牌。现有AI后台任务仍由创建人发起、查询及取消。

## 权限与数据

新增recruitment_position_viewer表，主键(position_id,user_id)，保存授权人和时间。按请求实时校验授权记录、岗位company_id，以及创建人/查看人当前的同公司成员关系。未授权、其他公司和已撤销授权的读取返回404；系统角色不绕过校验。授权及撤销按岗位锁串行，重复授权/撤销幂等；删除岗位在同事务中移除授权。

撤销后后续API访问立即拒绝，不能收回已下载或已经看到的内容。只读页面每10秒重新检查访问资格；刷新候选人或资料读取收到403/404也会清空页面并关闭抽屉。授权状态不复制进JWT。

旧岗位不会批量共享或自动迁移。只有创建人明确添加只读成员时，才在事务中核对成员关系并为company_id为空的旧岗位记录当前公司；原user_id、部门文字、department_id、候选人/文档/向量归属不变。若旧岗位存在进行中招聘任务，暂不补齐公司归属，提示任务结束后再授权，避免改变任务输入指纹。撤销授权不清空已核对的company_id。

## 接口与部署

- GET /api/v1/recruitment/positions/{id}/collaborators：仅创建人查看已授权成员。
- PUT 同路径，JSON {"userId": 数字}：仅创建人授权当前公司其他成员。
- DELETE 同路径/{userId}：仅创建人撤销，重复撤销无副作用。
- 岗位列表/详情响应新增canManage；只有创建人返回true。岗位、简历、匹配结果、已有问题与报告读取使用统一PositionAccess。

已有MySQL先备份并执行deploy/migrations/20261108_position_collaboration.sql，可重复执行；前置为此前公司/部门/岗位列升级。新库两份初始化SQL已同步。本阶段只新增授权表，不自动创建授权记录，不需要新增外部服务、密钥或Python依赖。

## 验证

PositionCollaborationTest在H2及MockMvc中覆盖显式授权/撤销、同公司未授权及跨公司隔离、管理员不绕过、成员关系变更、旧岗位归属确认与活动任务保护、全部读取族、写操作与任务查询取消拒绝、知识库/内部回调边界、岗位删除清理。AI网关使用mock，不调用真实模型。

scripts/verify-position-collaboration-ui.py使用模拟API验证创建人授权/撤销与加载失败重试、只读列表及已有资料、隐藏写操作、不轮询后台任务、撤销后清空页面和手机布局；其他岗位及任务UI脚本同步canManage响应契约。浏览器模拟接口验证不等同于真实写库联调。

手工验收：创建人先在“公司管理 → 成员管理”建立新HR账号，再打开自己的岗位授予只读权限。使用另一个浏览器会话登录该HR，确认只出现获授权岗位，可以查看已有资料但不能修改。创建人撤销后刷新HR岗位，应显示不可访问；未授权成员始终不能访问。AI生成请由创建人按需操作，本阶段不自动触发付费模型。

验证结果：mvn verify全量123项，118通过、5跳过，无失败/错误，其中本阶段协作权限10项。前端构建通过；授权/只读、岗位部门、匹配任务、简历重解析和资料生成五个Chrome模拟API脚本通过，包括移动端回归。本地真实MySQL在备份后连续升级两次，岗位、公司、成员及简历归属快照一致，授权表保持0条；没有自动给真实账号授权或触发模型调用。

本地运行服务已更新，登录后的岗位列表/详情及空授权列表GET通过，21个旧岗位均返回canManage=true且companyId仍为空，OpenAPI已注册授权接口，前端5173返回200。真实数据库验证为升级与只读检查；授权写入及越权场景在H2/MockMvc和浏览器模拟API中验证，尚未在真实MySQL上创建测试授权。
