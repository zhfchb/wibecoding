# 用户定位与权限规划

产品定位：面向中小型技术团队的AI招聘协作工作台。主要用户为公司管理员、HR/招聘负责人、技术面试官/用人负责人；候选人暂不直接登录。同一人未来可兼任多个岗位角色。

| 人群 | 目标职责 | 当前状态 |
| --- | --- | --- |
| 公司管理员 | 公司、部门、成员及权限维护 | 公司资料、成员和部门管理已实现 |
| HR/招聘负责人 | 岗位、简历、初筛及流程推进 | 已有招聘流程，公司内共享尚未开放 |
| 面试官/用人负责人 | 查看分配的岗位及候选人、面试准备与评价 | 规划；未新增实际角色、分配与评价接口 |
| 候选人 | 外部投递与进度查询 | 不在当前范围 |

## 分阶段执行

1. 已完成：公司基础与资料完善，按成员关系校验公司管理员/HR，角色不等同于系统ADMIN/USER。
2. 已完成：平级部门目录、公司内唯一名称、管理员增改启停、HR只读。无物理删除，无组织树。
3. 已完成：岗位关联正式部门ID，新选择校验当前公司且启用；旧部门文本保留，通过只读核对清单及详情页逐项关联，不自动猜测合并。新岗位记录company_id，旧岗位显式关联后补齐，创建人访问范围不变。
4. 下一阶段：公司招聘数据归属与共享权限。建立company_id和creator_user_id边界，覆盖API、后台任务、检索和Python回调；公司间严格隔离。HR并不默认拥有所有资料，知识库与私人聊天的共享规则需分别定义。
5. 后续独立阶段：面试官成员角色、岗位/候选人显式分配、限范围查看和面试评价；在访问边界测试前不开放全公司简历读取。

目前一人一家公司，不支持跨公司切换、既有账号直接合并、成员停用/复杂角色矩阵。公司目录可共享，不代表招聘资料已共享。系统ADMIN声明不能绕过公司HR的写权限。各阶段独立验证、Git提交，保留现有数据与已验证边界。
